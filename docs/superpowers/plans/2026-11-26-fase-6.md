# Fase 6 ZAP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** baseline y recorrido autenticado por PR, full/API manuales, reportes saneados y cinco hallazgos reales.
**Architecture:** job dast consume la imagen del build, espera IaC y usa red interna de Compose. Scripts oficiales ZAP con hooks ejecutan un recorrido AF autenticado y capturan cobertura; un wrapper valida resultados y publica solo reportes saneados.
**Tech Stack:** Docker, Python estándar + bibliotecas incluidas en ZAP, Automation Framework, GitHub Actions.
**Spec:** docs/superpowers/specs/2026-11-26-fase-6-design.md (copia del diseño aprobado en outputs).

## Global Constraints

- Rama fase-6-dast desde main4437a9f; preservar cambios ajenos y evidencia fase5.
- Solo instancia propia en red interna; sin secretos reales ni API ZAP publicada.
- FAIL10020/10021 para baseline/autenticado; resto WARN. Full/API hallazgos informativos, errores operativos bloqueantes.
- ZAP fijado por digest; imagen app idéntica al build. Reportes siempre, sin tokens/contraseñas.
- Sin push/merge ni cambios de protección de rama.

## Review Focus

- Reporte sin alertas no prueba cobertura: hook debe registrar URLs examinadas del objetivo real.
- HTTP200 anónimo no prueba autenticación: validar identidad y carrito de respuestas vistas por ZAP, más token inválido401.
- Configuración divergente entre baseline y autenticado: ambos usan rules.tsv y el mismo validador.
- Fallos de escáner o saneamiento: preservar fallo y no publicar archivos privados.
- API documentada solo B2B/orders: comprobar respuesta autenticada y limitar afirmaciones de cobertura.
